# tdd-loop — 시나리오 → red → green · refactor → verify

**전제**: `ticket-start` 를 마쳤고 착수 요약에 `TDD: 대상 — <근거>` 를 적었다. 이 스킬은 그 뒤, 코드 전이다.

순서가 값이다 — 테스트가 **먼저 실패해야** 그 테스트가 무엇인가를 검사한다는 것을 안다. 단계 제약(red 는 소스를 안 쓴다 · green 은 테스트를 안 고친다)은 **규약**이다: 막는 것은 없고, 지켰는지는 커밋 diff 와 코멘트로 읽힌다. 그러니 커밋을 단계마다 닫는다 — 그것이 읽기 단위다.

## 멈추는 곳은 둘 — 그리고 끝에 하나

**시나리오 표 뒤 · red 뒤** — 사람의 승인을 기다린다. 승인은 채팅으로 온다. 흔적은 남기지 않는다 — 다음 산출물(red 커밋 · green 커밋)이 곧 흔적이다. **verify 뒤** — 사람이 verifier 코멘트를 읽고 다음 절차를 지시한다.

## 절차

### 1. 시나리오 — 주 대화

1. **AC 항목마다** 시나리오를 도출한다 — 시그니처(API · 함수 · CLI)와 정상 · 경계 · 예외. **AC 밖도 더한다**(출처 열 "추가") — 경계값 · 예외 처리 · 입력 검증은 같은 약속의 가장자리다. *새 동작*을 더하려 한다면 그것은 범위 확장이다 — CLAUDE.md §3 (멈추고 묻는다).
2. target 이 여럿이면 **target 마다** 판정하고 표를 따로 낸다.
3. 표를 **티켓 코멘트**로 게시한다(`gh issue comment <N> -R jyoliar-lab/ops-workflow --body-file tmp/github-issues/<N>-scenarios.md`). 출력의 코멘트 ID 를 기록한다 — 수정은 ID 로만(`ticket-report` 4단계와 같은 이유).

```markdown
### TDD 시나리오 — <target repo>

| # | 시나리오 | 시그니처 | 종류 | 출처 | 테스트 이름 | 티어 | 의존성 처리 |
|---|---|---|---|---|---|---|---|
| 1 | … | `f(a, b) -> R` | 정상 / 경계 / 예외 | AC-1 / 추가 | `test_…` | 단위 / 통합 / e2e | 실제 / 녹화 replay / fake / mock·stub |
```

   **티어 · 의존성 처리 열은 이 티켓의 검수용이 아니다** — 아직 정해지지 않은 테스트 정책의 증거다. 무엇을 골랐고 왜 골랐는지를 표 아래 한 줄로 적는다.
4. **멈춘다.** 승인을 기다린다. 수정 요청이 오면 새 코멘트가 아니라 기록한 ID 로 그 코멘트를 **지정 수정**하고 다시 기다린다.

### 2. red — 주 대화

1. 표의 **테스트 이름 그대로** 테스트를 쓴다. 저장소의 테스트 규약(`.claude/rules/*` · `CLAUDE.md` · 기존 테스트의 자리와 모양)을 따른다 — 하네스가 아니라 저장소가 정한 것이다.
2. 소스는 **stub 까지만** — 시그니처 + `raise NotImplementedError` / `panic("TODO")` / `throw new Error("TODO")`. 본문을 쓰지 않는다. 컴파일이 살고, 신규 테스트만 실패하고, 나머지는 통과하는 최소가 stub 의 하한이다.
3. 저장소의 테스트 명령을 돌린다. **신규 전부 fail · 기존 전부 pass** 가 red 다. 통과해 버린 신규 테스트는 동어반복 후보다 — 고치고 다시 돌린다. 기존이 깨졌으면 stub 이 모자란 것이다.
4. **커밋 하나**: `test(#<N>): red — 시나리오 <k>개`.
5. **Draft PR 을 연다**: `ticket-pr.py <N> --draft --title "<제목>" --body-file tmp/pr/<N>.md`. 본문은 링크와 체크리스트뿐이다 — 대조표를 복사하지 않는다(사본은 낡는다):

```markdown
TDD — 시나리오: <시나리오 코멘트 URL>

- [x] red
- [ ] green
- [ ] refactor
- [ ] verify
```

6. 실행 결과를 **티켓 새 코멘트**로: 테스트 이름별 fail/pass · red 커밋 sha · PR 링크. (GitHub 이슈에는 스레드가 없다 — "답글" 은 새 코멘트다.)
7. **멈춘다.** 사람이 PR diff 에서 테스트 본문을 읽고 승인한다 — 시나리오 승인은 티켓에서(*무엇을* 검사하나), red 승인은 PR 에서(*어떻게* 검사하나).
8. 여기서 **시나리오가 틀렸음**을 알게 되면 조용히 고치지 않는다 — 표를 새 코멘트로 다시 내고 1단계로.

### 3. green + refactor — subagent `tdd-green`

1. Agent 도구로 **`tdd-green`** 을 부른다. 넘기는 것: 티켓 번호와 타입(커밋 메시지용) · target · worktree 경로 · red 커밋 sha · 저장소 테스트 명령. **넘기지 않는 것**: 티켓 본문 · 시나리오 표 · 주 대화의 구현 생각 — **테스트가 명세의 전부**이고, 그 의도를 모른 채 구현하는 것이 이 격리의 값이다.
2. 복귀는 green 커밋 · refactor 커밋 sha 와 실행 결과, 또는 **"구현 불가" 보고**다. 보고면 멈추고 사람에게 — 시나리오나 AC 가 틀렸다는 뜻이고, 테스트를 고치는 길은 사람 승인 뒤 2단계로 되돌아가는 것뿐이다.
3. PR 체크리스트를 갱신한다(`gh pr edit <PR> -R <repo> --body-file tmp/pr/<N>.md`) — subagent 가 아니라 주 대화가 한다.

### 4. verify — subagent `ac-verifier`

1. **`preflight.py <N>`** 먼저 — 기계 확인이 막히면 verifier 를 돌릴 이유가 없다. Draft PR 이 열려 있고 마지막 커밋의 체크가 초록이면 통과한다(red 커밋의 빨강은 지나간 런이다 — 의도된 것).
2. Agent 도구로 **`ac-verifier`** 를 부른다. 넘기는 것: 티켓 번호 · target · worktree 경로 · 시나리오 코멘트 URL · red/green/refactor 커밋 sha · PR URL · 테스트 명령. verifier 가 **직접 게시**하고 코멘트 링크만 돌려준다.
3. 체크리스트를 갱신한다.
4. **멈춘다.** 사람이 verifier 코멘트를 읽고 다음을 지시한다 — `gh pr ready` / 반증 테스트를 시나리오에 더해 red 로 되돌림 / 보완. **`gh pr ready` 는 지시 뒤다.**
5. 이후는 `ticket-report` — 단, 대조표는 verifier 가 이미 게시했다. 그 스킬의 2·3단계는 verifier 코멘트가 대신하고, 4단계(게시 후 검수 · 지정 수정)부터 이어진다.

## 재개 — 새 세션에서

`ticket-run.py` 가 보이는 코멘트 · 진행 커밋 · PR 에서 어느 단계까지 왔는지 읽는다 — 시나리오 코멘트가 있다 / red 커밋과 Draft PR 이 있다 / green · refactor 커밋이 있다 / verifier 코멘트가 있다. **승인 여부는 흔적에 없다** — 추측하지 않고, 파악한 현황을 사람에게 보이고 어디서부터 이어갈지 확인받은 뒤 진행한다.

## 하지 않는 것

- red 뒤에 소스 본문을 쓰는 것 · green 뒤에 테스트를 고치는 것 — 테스트가 틀렸으면 사람에게, 승인 뒤 2단계로.
- 승인 없이 다음 단계로 넘어가는 것.
- verifier 를 건너뛰고 스스로 대조표를 쓰는 것.
- 저장소에 테스트 러너 · 커버리지 도구를 **설치**하는 것 — 그것은 저장소의 결정이다. 러너가 없으면 애초에 판정이 비대상이었어야 한다.
