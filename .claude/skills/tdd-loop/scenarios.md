# 1. 시나리오 — 무엇을 검사할 것인가를 먼저 소유한다

주 대화가 한다. 코드 전이다. 산출물은 **티켓 코멘트 묶음**(target 마다) — **단위 코멘트** 하나씩(시그니처 절 + 시나리오 표 + 그 단위의 AC 커버리지)과, 단위가 둘 이상이면 **공통 · 색인 코멘트** 하나. 사람은 **단위마다** 승인하고, 승인된 단위부터 red 로 간다 — 그 승인의 순간이 "무엇을 검사할 것인가" 의 소유 시점이다.

## 1. 시그니처 — 이름과 형태를 먼저 고정한다

테스트가 부를 것의 **이름 · 파라미터 · 반환 · 오류**를 정한다. 구현이 아니다 — 본문은 없다. 기존 코드의 관례를 읽고 그대로 따른다; 신조어를 만들지 않는다. 읽을 곳 넷:

- **타입이 사는 자리** — 같은 종류의 타입이 어느 모듈에 어떤 형식(dataclass · struct · interface)으로 있나
- **같은 층의 이웃** — 비슷한 함수의 동사 · 인자 순서 · 반환 꼴(`parse_*` · `*_run` · `fetchX/createX`)
- **오류 방식** — 예외 클래스인가 · Result 인가 · no-op 인가, 문구의 결
- **기존 테스트의 이름** — 테스트 이름 열이 따를 관례

네 요소를 빠짐없이 — 해당 없으면 "없음" 으로 적는다(빈칸과 다르다):

| 요소 | 무엇 | 템플릿의 어디에 · 어떻게 |
|---|---|---|
| **타입** | 새 타입 · 기존 타입에 더하는 필드 | 그 타입을 **쓰는 단위**의 `#### 타입 · 상수` 블록 — 그 언어의 선언(dataclass · struct · interface). 둘 이상의 단위가 쓰는 타입만 색인의 공통 블록에. 필드 옆 주석은 "빈 것의 뜻" 까지만 |
| **함수 / API / CLI** | `def f(a: str, *, limit: int = 10) -> Result` · `GET /notes?tag=` · `obs promql --labels` | **그 시나리오 블록의 머리** — fence 한 줄, 본문은 `...`. 읽는 사람이 입력 · 출력을 위로 올라가 찾지 않게. 한 선언은 한 곳에만 |
| **오류 케이스** | 어떤 입력에서 무엇을 던지나 — **그리고 무엇을 조용히 무시하나(no-op)**. 던지지 않는 것도 결정이다. 예외 시나리오의 원천이 여기다 | 선언 줄 끝(또는 바로 아래) 주석 — `# ObsError: … · no-op: …` |
| **인터페이스** (프론트 Props · CLI 플래그 · 응답 형태) | 밖에서 보이는 형태 | 그 단위의 `#### 인터페이스` 블록 — 그 자체의 표기(CLI usage · `METHOD /path` · Props). 단위 전체가 공유하는 것(공통 플래그)은 색인에 |

**선언은 형태만이다** — 이름 · 인자 · 반환 · 오류. 타입 블록 아래 `관례:` 한 줄 — 어느 기존 이름 · 오류 방식을 따랐나(사람이 "왜 이 이름인가" 를 묻지 않게). 오류 케이스가 함수 여럿에 걸쳐 길면 줄 끝 주석 대신 `#### 오류 케이스` 목록으로. 정렬 규칙 · 상한 · 요청 수 같은 **행동은 시나리오 행**에 간다; 둘 다에 쓰면 대조할 원천이 둘이 된다. 타입 블록 + 각 블록 머리의 선언이 곧 red 의 stub 이다([red.md](red.md) §1).

기존 시그니처를 **바꾸는** 것이면 그 사실과 호출자를 적는다 — red 의 stub 범위가 거기까지 넓어진다.

**선언을 먼저 보인다** — 시그니처가 셋을 넘거나 · 새 타입이 생기거나 · 기존 시그니처를 바꾸면, 행을 쓰기 전에 선언들(타입 블록 + 각 fence + 층 지도 + 단위 나누기)만 채팅으로 보이고 한마디를 받는다. 이름이 흔들리면 행 · 테스트 이름 · stub 이 셋 다 흔들린다 — 54행 뒤에 이름을 고치는 것보다 싸다.

## 1.5 층 — 시나리오는 그 층이 더한 것에 붙는다

변경이 여러 층을 지나면(파서 → 조립 → CLI · 도메인 → 서비스 → 컨트롤러) **층마다 진입점 하나 = 블록 하나**, 블록 첫 줄에 **더하는 것** — 아래 층 대비 이 층이 새로 하는 일 한 줄.

| 역할 | 더하는 것 | 예 |
|---|---|---|
| **계산 · 도메인** | 값 · 규칙 · 예외 | `parse_metric` · `SeparateIds` · 엔티티 규칙 |
| **변환** | 모양 · 직렬화 | `*_lines` · `convertSourceDetail` · DTO |
| **조립** | 배선 · 순서 · 호출 수 · 오류 전파 | `promql_run` · `FindNewJobPostingApp.Run` · 서비스 |
| **경계 — 진입** | 입력 파싱 · exit / 상태코드 | `promql_main` · `main` · 컨트롤러 |
| **경계 — 외부 호출** | 프로토콜 · 실 응답의 형태 | `Client` · `wanted.List` · 리포지토리 |

- 한 주장은 **가장 낮은 층 하나**에. 위 층은 아래 층의 경우들을 **다시 열거하지 않는다** — 배선이 보이는 최소 예 하나뿐. 아래가 바뀔 때 둘이 깨지면 중복이다.
- 판별: Then 을 확인하는 데 **협력자의 대역**(인터페이스 구현체)이 필요 없으면 조립 시나리오가 아니고, **프로세스 경계**(argv · env · stdout · HTTP · gRPC 메시지)가 필요 없으면 경계 시나리오가 아니다 — 한 층 내린다.
- 파일 배치(디렉터리 · 티어)는 저장소 규칙이 정한다. 이 스킬은 **어느 층이 어떤 주장을 소유하나**만.

## 1.6 단위 — 코멘트는 세로로 자른다

층은 가로다. 코멘트는 **세로**로 자른다 — **단위 = 기능 하나**: 그 기능의 계산 · 조립 · 변환 · 진입 함수와, 그 기능**만** 쓰는 타입 · 상수 · 인터페이스가 한 코멘트에 모인다. 읽는 사람이 `histogram` 의 시그니처 · 타입 · 행을 한 화면에서 보고 승인하게 — 타입이 100줄 위의 블록에 모여 있으면 행을 읽을 때 그 타입을 다시 찾아 올라간다.

- **둘 이상의 단위가 쓰는 것**(이동하는 타입 · 공유 진입 `*_run` 의 디스패치 · 공유 헬퍼)만 **공통 · 색인** 코멘트로 올린다. 공통의 함수도 자기 행을 갖는다 — 그 행은 **첫 단위의 red** 에 들어간다.
- **단위가 하나면 코멘트 하나**다. 색인은 없다 — 층 지도 · 결정은 그 코멘트에.
- 단위를 가르는 자리는 보통 티켓이 이미 말한다 — 동작 AC 가 기능 하나씩을 가리키면 그것이 단위다. AC 하나가 여러 단위에 걸치면(`AC-6 네 함수 각각이 "없음" 을 낸다`) 단위마다 자기 몫의 행을 갖고, 색인의 단위 표가 그 AC 를 각 단위에 적는다.
- 메커니즘 하나가 함수 여럿을 가로지르는 변경(기록 · 로깅 · 반환 꼴 통일)은 단위가 하나다 — 억지로 함수마다 가르지 않는다. 가르는 기준은 "따로 승인해도 뜻이 서나" 다.
- 한 코멘트가 한도(65k)를 넘으면 단위가 너무 크다는 신호다 — 더 가른다. 게시 스크립트가 거부한다.

## 2. 시나리오 — Given / When / Then

시그니처의 각 항목마다 **정상 · 경계 · 예외**를 뽑는다. **한 행 = 결과 하나** — 한 테스트가 된다. 형식은 GWT — 세 칸이 나중에 테스트 코드의 세 부분이 된다.

| 종류 | 뜻 |
|---|---|
| **정상** | 행복 경로 — 일반 입력의 기대 동작 |
| **경계** | 상한 · 하한 · 빈 것 · 하나 · 같은 값 · 마지막 요소 |
| **예외** | 잘못된 입력 · 외부 실패 · **무시돼야 할 입력**(시그니처의 no-op) |
| **가드** | 이미 되는 동작이 **유지된다** — Bug 티켓의 회귀 방지 · 시그니처 변경 뒤 호출자 · `기존` 테스트가 그대로 검사하는 행(§2.5). **red 에서 통과가 기대되는 유일한 종류**다. 승인된 행만. 가드는 그것을 소유한 단위에 — 공통에 모으지 않는다 |

- **동작 AC 하나마다** 최소 하나. 한 AC 가 여러 행을 낳는 것이 보통이다. **검사 · 선언 · 수렴 · 지속 AC 는 시나리오 행을 낳지 않는다** — 테스트가 아니라 다른 근거로 대조되는 약속이다(verifier · ticket-report). 그 AC 에 행을 억지로 만들면 구조 테스트가 된다.
- **AC 밖도 더한다**(출처 `추가`) — 경계값 · 빈 입력 · 예외 처리는 같은 약속의 가장자리다. 코드를 읽어야 보인다.
- **새 동작은 더하지 않는다** — AC 에 없는 기능은 범위 확장이다. CLAUDE.md §3.
- **행을 다 뽑은 뒤 기존 테스트와 대응한다**(§2.5) — 출처 칸은 AC 의 것이고, 테스트가 신규인지 기존인지는 테스트 이름 칸의 표식이 말한다.
- **Bug 티켓의 첫 행은 언제나 재현**이다 — 버그의 입력(Given · When)에 기대 동작(Then)을 단언한다. red 에서 실패해야 재현된 것이다. 그다음 행들이 `가드`(고치면서 깨지면 안 되는 것)다.
- **번호는 묶음 전체의 통번호이고 영구다.** 행을 지우면 그 번호는 결번으로 남기고(`~~23~~` 또는 "23 결번"), 새 행은 끝 번호 다음을 받는다. 번호를 다시 매기면 red 커밋 · 검수 코멘트 · 편집 이력이 가리키던 행이 전부 어긋난다.

## 2.5 기존 테스트와 대응한다 — 행을 다 뽑은 뒤에

순서가 값이다: **① 행을 전부 뽑는다 → ② 기존 테스트를 읽는다 → ③ 행마다 대응한다.** 기존 테스트를 먼저 읽으면 "이미 있는 것" 에 맞춰 행을 줄이게 되고, 읽지 않으면 같은 것을 두 번 쓴다 — 둘 다 스위트를 흐린다. 읽는 범위는 그 단위가 건드리는 모듈의 테스트 파일과 그 픽스처 · 대역이다. 저장소 전체가 아니다.

행마다 셋 중 하나다 — 테스트 이름 칸에 적는다:

| 표식 | 뜻 | red 에서 |
|---|---|---|
| `test_x` (표식 없음) | 신규 | 새로 쓴다 — fail 이어야 한다 |
| `기존 test_x` | 기존 테스트가 그대로 이 행을 검사한다 | 쓰지 않는다. 종류는 **가드** — pass 가 정상 |
| `수정 test_x — 무엇을 더하나` | 기존 테스트에 **더해서** 이 행을 검사한다 — 단언 추가 · parametrize id 추가 · 픽스처 확장 | 더한다 — 더한 뒤 fail 이어야 한다. 그대로 통과하면 더한 것이 없는 것이다 |

**수정은 더하기만이다.** 기존 단언을 빼거나 Then 을 바꾸면 옛 동작의 회귀 가드가 사라진다 — 그것은 수정이 아니라 **대체**다: 새 행(신규)을 쓰고 옛 테스트는 처분 표에 `대체` 로 적는다. 시그니처가 바뀌어 옛 테스트가 옛 꼴로 더는 살 수 없을 때가 전형이다.

**기존 테스트 처분 표** — 단위 끝(AC 커버리지 앞)에, 이번에 건드리는 기존 테스트 **전부**:

```markdown
#### 기존 테스트 처분

| 기존 테스트 | 처분 | 행 |
|---|---|---|
| `test_defaults_when_nothing_set` | 그대로 | 3 |
| `test_templates_raw_carries_examples` | 수정 — 단언을 `client.log` 로 | 9 |
| `test_single_call_raw_*` (4) | 삭제 — 주장이 구조적으로 됨(기록이 `Client` 로) | — |
| `test_around_raw_carries_count_and_both_sides` | 대체 | 10 |
```

행 표식만으로는 **삭제**와 **대체**가 안 보인다 — 지워질 테스트에는 행이 없다. 처분 표가 "기존 스위트에 무엇이 일어나나" 의 목록이고, red 검토자는 red diff 가 이 표의 테스트만 건드렸는지 대조한다. 건드리는 기존 테스트가 없으면 절째 지운다.

## 3. 형식 — 템플릿을 복사해 채운다

구조를 기억으로 재구성하지 않는다. 파일은 단위마다 하나, 색인이 있으면 하나 더:

```bash
cp .claude/skills/tdd-loop/scenarios.template.md tmp/github-issues/<N>-scenarios-<repo>-<단위>.md
cp .claude/skills/tdd-loop/scenarios.index.template.md tmp/github-issues/<N>-scenarios-<repo>-index.md   # 단위 둘 이상일 때
```

`<…>` 를 채우고 `<!-- -->` 주석은 지운다. 비는 절 · 비는 종류는 **절째** 지운다. 단위 하나짜리 완성본의 꼴은 [scenarios.example.md](scenarios.example.md) — 시그니처 둘(계산 · 진입) · 예외 · 가드 · AC 커버리지. 여러 단위의 완성본은 ops-workflow #94 의 코멘트 묶음(색인 하나 + 연산 넷).

**머리 줄이 코멘트의 열쇠다** — `### TDD 시나리오 — <owner/repo> — <단위>`. 색인은 단위 자리에 `공통 · 색인`. 같은 머리로 다시 게시하면 새 코멘트가 아니라 그 코멘트가 갱신된다(§4). 머리 아래의 판 · 승인 줄과 진행 표(승인 뒤 단계를 지날 때마다 red · green · verify 행 하나씩 덧붙는다)는 스크립트가 쓴다 — 파일에 적지 않는다. 산문으로 "무엇이 바뀌었나" 를 적지도 않는다 — 변경은 GitHub 의 편집 이력이 보인다. 그래서 단위 코멘트 하나가 그 단위의 스레드다 — 시나리오와 진행이 한 자리에 있다.

| 자리 | 어디에 | 규칙 |
|---|---|---|
| 층 지도 | 색인 (단위 하나면 그 코멘트) · 시그니처 셋 초과일 때만 | 층 · 이름 · 부르는 것 — 전체 그림 한 표 |
| 단위 표 | 색인 | 단위 · 코멘트 URL(`{url:<단위>}` — 스크립트가 채운다) · 담당 AC. **모든 동작 AC 가 어느 단위엔가 있어야 한다** — 다른 그룹의 AC 는 단위 표에 오르지 않는다 |
| 결정 | 색인 (단위 하나면 그 코멘트) | 티켓과 다른 자리 — 사람 확인을 받은 것만 |
| 타입 · 상수 | 쓰는 단위 · 둘 이상이 쓰면 색인 | 코드 블록(모듈마다). 함수 선언은 여기 두지 않는다 |
| 인터페이스 | 그 단위 · 공유 플래그는 색인 | 그 자체의 표기 블록. 없으면 절 삭제 |
| 시나리오 블록 | 그 단위 · 공통 함수는 색인 | **블록 = 시그니처 하나**가 기본. 제목은 이름, 머리는 **그 선언의 fence**(본문 `...` · 오류 주석). 같은 층 · 같은 Given 꼴이면 한 블록에 선언 여럿도 된다. 블록 안은 종류(정상 · 경계 · 예외 · 가드)마다 작은 표, 비는 종류 생략, 번호는 묶음 전체 통번호 |
| 더하는 것 | 블록 첫 줄 | 아래 층 대비 이 시그니처가 새로 하는 일 — **한 줄**. 넘치면 행으로 내려간 것이다 |
| Given | 행 | 전제 — 상태 · 입력 · 외부의 응답. 픽스처의 우연("65줄")이 아니라 성질("스트림 둘") |
| When | 행 | 한 번의 호출 — 시그니처의 이름 그대로 |
| Then | 행 | **결과 하나** — 성질("없다" · "거부한다" · "1회다"). 결과 하나의 여러 성질(`ObsError` · 문구에 경로 · 문구에 env 이름)은 **한 행, 단언 여러 줄**. 결과가 둘(반환값과 부수효과 · 응답과 호출 수)이면 두 행 |
| 테스트 이름 | 행 | 저장소 규약대로. red 에서 **이 이름 그대로**. red 검토자가 이 이름으로 대조하고, verifier 의 대조표 근거 칸이 이 이름이다. 기존 테스트면 표식(`기존` · `수정 — 무엇을 더하나`, §2.5). **Given 만 다르고 When · Then 이 같은 행들**(없는 경로 / 디렉터리)은 parametrize 테스트 하나 — 이름은 같고 `[id]` 로 구분, 행은 그대로 |
| 티어 · 의존성 | 단위 끝 | 이 티켓의 검수용이 아니다 — 아직 정해지지 않은 테스트 정책의 **증거**. 왜 를 끝에 한두 줄로 |
| 실측 · 근거 | 단위 끝 | API 응답 형태 · 실환경 확인 — `<details>` 로 접어 **표 아래에**. 시그니처를 밀어내지 않는다 |
| 기존 테스트 처분 | 단위 끝 · AC 커버리지 앞 | 이번에 건드리는 기존 테스트 전부 — 그대로 · 수정 · 삭제 · 대체 와 대응 행(§2.5). 없으면 절 삭제 |
| AC 커버리지 | **단위마다** 끝 | 그 단위가 담당하는 동작 AC 전부가 한 행 이상. 동작 AC 인데 테스트로 못 잡으면 그 사실을 적고 사람에게 — 다른 그룹의 AC 는 이 표에 없다 |

## 4. 게시 — 스크립트로

```bash
scenario-post.py <N> --repo <owner/repo> tmp/github-issues/<N>-scenarios-<repo>-*.md
```

단위 파일과 색인 파일을 한 번에 넘긴다 — 색인의 `{url:<단위>}` 를 채우려면 단위가 먼저 게시돼야 하고, 순서는 스크립트가 잡는다. 머리가 같은 코멘트가 이미 있으면 PATCH 다 — 새 세션이어도 같은 자리로 간다. 출력의 단위 · 판 · URL 이 red 커밋 · PR 본문 · 검토자 호출에 들어간다.

파일 하나만 넘겨도 된다 — 한 단위만 고쳤을 때. 갱신해도 승인 줄과 진행 표는 그대로 남는다 — 판만 오른다.

## 5. 멈춘다 — 단위마다 승인

게시했으면 **멈추고 기다린다.** 사람은 색인(공유 타입 · 결정 · 단위 표)을 먼저 보고, 단위를 하나씩 본다. 승인은 채팅으로 **단위 이름과 함께** 온다 — "histogram 승인" · "색인과 around 승인".

- **색인이 먼저다.** 공유 타입은 모든 단위의 stub 이고 단위 표는 AC 의 분배다 — 색인 승인 전에는 어느 단위도 red 로 가지 않는다.
- **승인이 오면** 표식을 붙이고 그 단위를 [red.md](red.md) 로 보낸다 — 다른 단위가 아직 수정 중이어도:
  ```bash
  scenario-post.py <N> --repo <owner/repo> --approve "<단위>"
  ```
  승인은 그 판에 붙는다 — 뒤에 본문이 바뀌면 판이 오르고 승인은 옛 판 번호로 남아, "승인 뒤 바뀌었다" 가 코멘트 머리에서 읽힌다.
- **수정 요청** → 파일을 고치고 §4 를 다시 — 그 코멘트가 PATCH 된다. 다시 기다린다. "좋아요" 한마디로 남은 지적을 건너뛰지 않는다 — 단위 이름이 붙은 명시적 승인까지.
- **"추가" 행이 범위 밖** → 지운다. 필요하다고 보면 이유를 말하되 판정은 사람의 것.
- **뒤 단계에서 표가 틀렸음을 알았을 때**(red 검토자 blocked · green 중단 · verifier 발견)도 같다 — 파일을 고치고 §4 로 PATCH, 그 단위의 재승인. 행은 더하거나 결번으로 — 번호를 다시 매기지 않는다(§2). 바뀐 행만 red 를 다시 쓴다.
- **판정 자체가 뒤집히면**(비대상) 스킬을 나간다 — 코멘트는 남긴다.

## 흔한 실수

- **시나리오가 구현을 말한다** — "캐시에 저장한다" 는 구현이다. 밖에서 보이는 약속: "두 번째 호출은 요청을 보내지 않는다".
- **한 행에 결과 둘** — "거부하고 로그를 남긴다" 는 두 행(예외와 부수효과).
- **결과 하나를 행 여럿으로** — "`ObsError`" · "문구에 경로" · "문구에 `OBS_CONFIG`" 는 같은 Given · When 의 같은 결과다. 한 행, 단언 셋. Given · When 칸에 "같음" 이 늘어서면 접는다.
- **Given 에 픽스처 값** — "65줄을 돌려준다" 는 재녹화에 깨진다. "스트림 수만큼" 이 약속.
- **동작 AC 6개 중 5개만** — 단위마다 커버리지 표를 채우고 색인의 단위 표가 동작 AC 전부를 분배하면 보인다. 표 없이 넘어가지 않는다.
- **검사 · 선언 AC 에 시나리오 행을 만든다** — "mutation score ≥ 80 %" · "명세에 `POST /x` 가 있다" 는 테스트가 아니다. 행을 쓰지 않는다 — verifier 가 검사 · 검증기로 대조한다(§2).
- **Given 을 손으로 만들 수 없다** — "실 사이트의 지금 공고" · "실 DB 의 행" 은 Given 이 아니다. 층이 틀렸거나 대역이 없는 것 — 의존성 열에 `실 API` 로 적고 승인 때 사람이 본다.
- **위 층이 아래 층의 경우를 다시 센다** — `Run` 테스트가 "전부 새것 · 전부 저장됨 · 섞임" 을 다시 돌면 `SeparateIds` 의 표를 복사한 것. 배선 예 하나로 줄인다.
- **시그니처를 정하지 않고 시나리오부터** — 이름이 흔들리면 테스트 이름 · stub · 구현이 셋 다 흔들린다.
- **기존 테스트를 안 읽고 전부 신규로** — 같은 Given · Then 이 두 이름으로 산다. 행을 다 뽑은 뒤 스위트를 읽는다(§2.5).
- **"수정" 이 단언을 뺀다** — 옛 가드가 사라진다. 빼야 하면 대체다 — 새 행 + 처분 표.
- **단위를 층으로 자른다** — "계산 코멘트 · 조립 코멘트" 는 타입을 다시 한자리에 모은다. 단위는 기능이다(§1.6).
- **타입을 전부 색인에** — 한 단위만 쓰는 타입이 색인에 있으면 그 단위를 읽을 때 또 올라간다. 공통은 둘 이상이 쓰는 것뿐.
- **새 코멘트로 다시 낸다** — 같은 머리의 코멘트가 있으면 스크립트가 PATCH 한다. 손으로 `gh issue comment` 를 치는 길은 이 단계에 없다.
- **종류가 애매해서 새 분류를 만든다** — 정상 · 경계 · 예외 · 가드 넷뿐이다. 어디인지 애매하면 사람에게 묻는다.
